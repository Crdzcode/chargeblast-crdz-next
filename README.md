# Chargeblast Project — Stripe Payments screen

A rebuild of the Stripe Dashboard **Transactions → Payments** screen for the Chargeblast
front-end project, built with **Next.js 16 (App Router), React 19 and TypeScript (strict)**.
All data is a local, deterministic mock: no account, API or backend is needed.

## Features

**Required by the brief**

- Payments table with **Payment ID** (abbreviated, full value in a tooltip, copy button that only
  confirms after the clipboard write succeeds), **Customer**, **Amount** with its currency,
  **status badges** (Succeeded, Pending, Failed, Refunded), **payment method** (brand tiles and last
  4 digits) and **Date** (date and time, relative time in a tooltip on hover or keyboard focus).
- Sorting by date, amount and status (ascending/descending, deterministic ties).
- Pagination with 25, 50 or 100 rows per page.
- Filters: date range (**Today, Last 7 days, Last 30 days, Custom**), status (multi-select), payment
  method (Card, ACH, Wallet — multi-select), amount range, plus Currency and Card brand ("More
  filters") as in the reference.
- Text search by payment ID, customer email or last 4 digits.
- About 1,000 realistic payments in four currencies (USD, BRL, EUR, GBP).

**Nice-to-haves (in the brief's order of preference)**

1. Left sidebar with the reference sections (Home, Balances, Transactions, Customers, Product
   catalog, Shortcuts, Products, Developers).
2. Top bar with a global search (suggests payments and customers, opens details) and an account
   menu (from the account switcher).
3. Payment details page at `/transactions/payments/[paymentId]` with a timeline of events, payment
   method, details and metadata; a real 404 for unknown IDs; the back link restores the filters you
   came from.
4. Saved filters (named, stored in this browser) **and** shareable URLs (every filter, the sort and
   the page live in the query string).
5. Column resizing (pointer or arrow keys) and drag-to-reorder (pointer or keyboard), persisted per
   browser; "Edit columns" also hides optional columns and resets the layout.
6. CSV export of the **current view** (every row matching the filters, in the current sort, all
   pages) or of the selected rows.

Also: the reference's status view cards (All, Succeeded, Refunded, Disputed, Failed, Uncaptured),
row selection, a row actions menu, loading/empty/error/not-found states and a mobile layout.

Sections and buttons that exist in the reference but are outside this demo (Home, Balances,
Create payment, Analyze, other Transactions tabs…) keep the reference look and say "Not available
in this demo" on hover and focus instead of pretending to work.

## Run locally

Requires **Node.js 20.9+** (developed with Node.js 24).

```bash
npm install
npm run dev
```

Open [http://localhost:3000](http://localhost:3000) (it redirects to `/transactions/payments`).

```bash
npm run typecheck     # tsc --noEmit (strict)

npm run build         # production build
```

## Mock data that does not go stale

The dataset is generated by `src/features/payments/data/generate-transactions.ts` from a fixed seed.
Every payment is a blueprint (ID, customer, amount, status, method…) placed **N days before today at
a fixed time of day**, so the data is a _daily snapshot_ relative to the request time:

- Today, Last 7 days and Last 30 days always have data, on any date the app is opened.
- A payment keeps the same ID and attributes; it is never created in the future (today's payments
  appear as their time of day passes, plus a few "live" ones in the last hour).
- Refund and dispute dates always fall after the payment and before today.
- No `Math.random()` or ad-hoc `new Date()` during rendering: the server reads the clock once per
  request (`getReferenceTime()`, after `connection()` so it is never frozen at build time) and only
  that number crosses to the browser, which rebuilds the identical dataset. Server HTML and hydration
  always match.

To pin the clock (screenshots, demos, E2E), set `PAYMENTS_REFERENCE_TIME` to an ISO instant, e.g.
`PAYMENTS_REFERENCE_TIME=2026-11-18T17:05:00.000Z npm run start`. The Playwright config does this.

### Dates and time zone

All dates are shown and filtered in the account time zone, **America/Sao_Paulo** (like Stripe shows
the account's zone), on the server and in the browser alike. Presets and custom ranges use whole
calendar days in that zone and **both ends are inclusive**. The helpers in `src/lib/time-zone.ts`
use `Intl` only and are tested for DST zones as well.

### Amounts across currencies

Sorting and the amount filter compare **nominal minor units** across currencies (no exchange rates
are invented). Combine the Amount filter with the Currency filter to compare a single currency; the
filter panel says this explicitly.

## How the code is organized

```text
src/
├── app/                                  # Routes only (App Router)
│   ├── (dashboard)/layout.tsx            # Shell: sidebar + top bar, reads the request clock
│   └── (dashboard)/transactions/payments/
│       ├── (list)/page.tsx|loading|error # Payments list (its own loading/error boundary)
│       └── [paymentId]/page.tsx          # Payment details (+ not-found)
├── components/
│   ├── layout/                           # Sidebar, top bar, global search, account menu
│   └── ui/                               # Small Radix-based primitives styled with the tokens
├── features/payments/
│   ├── model/                            # Transaction, query, status views, column model
│   ├── lib/                              # Pure logic: pipeline, URL, dates, CSV, saved filters, timeline
│   ├── data/                             # Seeded generator, repository, request clock, provider
│   ├── hooks/                            # URL query state, column preferences, saved filters
│   ├── components/                       # Table, cells, filters, toolbar, details
│   └── __tests__/                        # Unit and component tests
├── lib/                                  # Cross-cutting helpers (time zone, storage, clipboard)
└── app/globals.css                       # Tailwind 4 theme: tokens sampled from the reference
e2e/                                      # Playwright end-to-end tests
```

**State has one owner each**: the query (filters, search, sort, page) lives in the **URL**; column
preferences and saved filters live in **localStorage** (read with `useSyncExternalStore`, so the
first render matches the server); selection is component state. A single pure pipeline —
**search → filters → sort → paginate** — derives everything, so there is no store to keep in sync.

## Why Next.js, and why these libraries

The brief prefers Next.js with TypeScript. The App Router keeps routing, the loading, error and
not-found boundaries and the request clock on the server. The domain rules (filters, sorting, URL
format, CSV, saved filters) are framework-free TypeScript with their own unit tests.

| Library                 | Why                                                                                  |
| ----------------------- | ------------------------------------------------------------------------------------ |
| Tailwind CSS 4          | Design tokens as a theme, no runtime CSS-in-JS                                       |
| Radix UI (`radix-ui`)   | Accessible popover, tooltip, menu, checkbox and dialog behavior, styled from scratch |
| dnd-kit                 | Column reordering with pointer **and** keyboard support                              |
| lucide-react            | Icons                                                                                |
| Vitest, Testing Library | Unit and component tests                                                             |
| Playwright              | End-to-end tests on the production build                                             |

Deliberately **not** used: a state library (the URL and the pure pipeline are enough), TanStack
Table (the column model already drives sorting, sizing, order and visibility, and a second model
would duplicate it), shadcn default styles (they would move the look away from Stripe), and a web
font (the reference uses the system font stack, as Stripe does).

## Known limitations

- Data is mocked in memory; nothing is persisted on a server.
- Saved filters and column preferences are per browser (localStorage), not per account.
- "Status" has a visible column header so it can be sorted; in the reference the badge column has
  no header. The required **Payment ID** column is added before **Date**, where the reference has no
  such column.
- Out-of-scope dashboard areas are visual placeholders with a "Not available in this demo" hint.
